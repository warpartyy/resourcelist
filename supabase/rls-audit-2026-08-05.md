## Live Policy Inventory

The repository currently contains only one Supabase migration:

- `20260805000100_create_resource_guide_intelligence_events.sql`

That migration enables RLS on `resource_guide_intelligence_events` and creates one service-role insert policy.

A read-only Supabase REST attempt to inspect `pg_policies` returned HTTP 404, so the live policy inventory could not be read from this workspace without a direct database connection or SQL admin tooling. The recommended migration therefore uses `pg_policies` checks at migration time and only creates each named policy when it is missing.

## Admin Role Basis

The app treats a user as an administrator when `profiles.role = 'admin'`.

The migration adds two security-definer helpers:

- `resource_list_current_user_is_admin()`
- `resource_list_profile_public_fields_unchanged(uuid, text, text)`

The second helper allows users to update profile display fields while preventing self-escalation through `role` or `email` changes.

## Specific Workflow Findings

### Public Directory

`resources` is read from public pages and search services. Anonymous users should not see pending, rejected, deleted, or admin-only resource records. Recommended policy: public read only for `status = 'approved'`.

### Resource Submissions

The public suggest-resource form inserts directly into `resources` with `status = 'pending'`. The update suggestion API inserts into `resource_submissions` with `type = 'update'`. Recommended policies preserve those inserts without allowing public updates or public reads of submissions.

### Resource Comments

`components/admin/CommentsSection.tsx` uses the browser Supabase client for:

- `SELECT` comments by `resource_id`
- `INSERT` comments
- `UPDATE` comments
- `DELETE` comments

The reported HTTP 403 regression is consistent with RLS being enabled on `resource_comments` without an authenticated admin insert policy. The migration restores admin-only comment CRUD.

### Admin Mentions

Mentions depend on:

- admin `SELECT` on `profiles` for mention lookup
- admin `INSERT` on `notifications`
- users reading/updating/deleting their own notifications

The migration restores this without exposing all notifications publicly.

### Profiles

Admin role logic depends on `profiles.role`. The migration does not add a broad public profile update policy. It allows self profile updates only when `role` and `email` remain unchanged.

### Resource Guide

Feedback and intelligence writes are server-side through `getSupabaseAdmin()`. The migration keeps direct client writes closed and adds only service-role insert plus admin read policies.

### AI Support Tables

No separate evaluation or benchmark database tables were found in `lib/database.types.ts`. Evaluation and benchmark systems appear file/service-based only.

## Recommended Migration

Use:

```text
supabase/migrations/20260805000200_restore_application_rls_policies.sql
```

Do not apply blindly in production before reviewing against the live policy list if direct database access is available. The migration is idempotent by policy name, but if equivalent policies already exist under different names, Postgres will keep both.

## Verification Plan

After applying to a staging database:

1. Public `/resources` and search show only approved resources.
2. Public resource suggestion creates a pending `resources` row.
3. Public update suggestion creates a pending `resource_submissions` row.
4. Admin can create, edit, and delete `resource_comments`.
5. Comment mentions create notifications.
6. Mentioned admins can view, mark read, and delete their own notifications.
7. Admin route guard can read `profiles.role`.
8. Profile settings can update display name without changing role/email.
9. Resource Guide feedback inserts through `/api/resource-guide/feedback`.
10. Intelligence collection inserts through server-side service role.
11. Admin intelligence reporting returns summaries.
12. Anonymous users cannot read pending resources, comments, messages, feedback, or intelligence events.
